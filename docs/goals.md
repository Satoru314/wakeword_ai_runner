# wakeword_ai_runner、ゴール

技術スタックを決める前段階として、何を実現したいアプリなのかを固めた設計メモ。作りやすさより速度とカスタマイズ性を優先する。

## コアバリュー

ウェイクワードで起動し、音声だけで手を離したままAIエージェントに指示を出し、結果を音声で受け取れる。完全ハンズフリーなAIエージェント操作を、誰でも導入できる配布可能なソフトウェアとして提供する。

## 基本フロー（v1スコープ）

常時、軽量にウェイクワードを待ち受ける。検知したら発話を1回分だけ聞き取り、単一コマンド・ワンショット型で完結させる。聞き取った内容をAIエージェントに渡して処理・実行させ、応答はTTSで読み上げて完結する。連続・マルチターン会話は今回は扱わず、将来拡張として据え置く。

```
[常時稼働・ローカル] ウェイクワード検知
        ↓ 検知
[クラウドAPI・ユーザーのキー] 発話を録音 → STT
        ↓ テキスト
[クラウドAPI・ユーザーのキー] AIエージェントに送信・実行
        ↓ 応答
[クラウドAPI・ユーザーのキー] TTSで音声化 → 再生
```

## 処理方式

ウェイクワード検知は常時稼働のバックグラウンド処理なので、レイテンシ・プライバシー・ランニングコストの観点からローカル完結を必須とする。それ以外のSTT、エージェント処理、TTSはクラウドAPI利用を前提とし、ユーザーが自分のAPIキーを入力するBYOK方式を理想とする。運営側でAPI利用料を肩代わりせず、配布物として提供しやすい形にする。エージェントは複数プロバイダに対応し、ユーザーが選べるようにする。

## 優先する非機能要件

速度は二段構え。ローカル常時稼働部分は誤検知・見逃しを抑えつつCPU/メモリ負荷を極小にし、クラウド部分は検知後のラウンドトリップ（録音からSTT、エージェント、TTS再生開始まで）の体感速度を優先する。

カスタマイズ性は作りやすさより優先し、ウェイクワード自体の変更・追加、STT/TTSエンジンの選択、各種クラウドAPIキーのユーザー設定、LLMプロバイダの切り替えをすべて対象にする。

## アーキテクチャ方針

切り替え可能な要素、ウェイクワード検知エンジン、STT、LLMプロバイダ、TTSはすべて共通インターフェースの背後に複数実装を持たせ、設定に応じて実行時に差し替えるStrategy/Adapterパターン的な構成で一貫させる。呼び出し側は共通インターフェースにのみ依存し、プロバイダ追加時に変更しなくて済むようにする。

## 対応プラットフォーム

Linuxを最優先とし、WindowsとmacOSは追加目標とする。

## 想定利用シーン

配布可能な製品/OSSとして、汎用性・設定のしやすさも視野に入れる。特定の自分専用ツールではなく、他の人にも使ってもらう前提。
